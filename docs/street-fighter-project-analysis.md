# Street-Fighter Championship 项目分析与协作计划

整理日期：2026-10-04。

本文用于 SYE6308 四人小组的项目启动、分工和实施讨论。依据为课程文件 `Project_List_2026.pdf` 第 1、8、9 页及老师提供的 Kaggle Notebook。下文分别标明课程要求、示例配置、实施建议和待确认事项；建议不能替代老师的正式评分与提交说明。

## 1. 项目定位

- 项目正式名称是 **Street-Fighter Championship**。
- 这是四人小组共同完成的课程 project。
- 项目目标是训练一个控制 **RYU** 的强化学习智能体，完成对电脑及其他小组智能体的对战。
- 资格赛与淘汰赛是这个课程项目内部的对战安排。不能据此假设对战名次就是全部项目成绩。
- PDF 为本项目标注 **×1.05** 的难度系数，第 1 页规定项目分数乘以难度系数。具体评分细则与个人贡献评分仍需向老师确认。

项目工作应覆盖环境运行、模型训练、改进实验、效果评估和最终提交。报告及展示是否需要、具体形式是什么，应以本项目的正式通知为准。

## 3. 文件明确写出的要求

### 3.1 技术要求

| 要求 | 对实现的影响 |
| --- | --- |
| 只能选择 RYU 训练 | 训练和评估围绕 RYU 开展 |
| 使用老师设置的环境 | 共用老师环境及输入信息，避免训练与正式对战接口不一致 |
| 禁止硬编码战术 | 不能手写“对手在位置 Y 就出升龙拳”等决策规则；动作应由学到的策略或价值函数决定 |
| 一个游戏帧内完成决策 | 需要测试完整推理入口的耗时；超时会被视为 inactive |
| 提供 `act(state)` | 最终模型必须能通过正式调用接口返回合法动作 |
| 使用组号与角色命名 | PDF 示例为 `group12_RYU.pth`；实际采用本组组号 |

禁止硬编码战术不意味着程序中不能出现任何 `if/else`。输入检查、环境结束判断与普通程序控制不同于手写战术。当前示例环境已经定义波动拳和升龙拳动作；让模型学习选择这些已有动作，应与自己编写情境战术规则区分。

### 3.2 项目内部对战安排

**资格赛：Agent RYU 对电脑 RYU。**

- 当参与队伍超过 8 组时，各组智能体分别与电脑 AI 对战。
- 智能体获胜时，根据完成比赛的用时排名。
- 智能体失败时，根据剩余血量排名；文件未明确是哪一方的血量。
- 前 8 组进入淘汰赛，对阵由资格赛成绩决定。

**淘汰赛：Agent RYU 对 Agent RYU。**

- 一方生命值降到 0，另一方获胜。
- 时间结束时，生命值更高的一方获胜。
- 生命值相同则为平局。

测试局数、同分处理、平局后的安排和具体计分方式未在 PDF 中说明。

### 3.3 提交描述中的歧义

PDF 将提交内容描述为包含 `act(state)` 的简单推理脚本 `.pth` 文件，这同时涉及脚本与模型文件，接口说明不够完整。

当前 PPO 训练示例保存的是 `.zip`，其他示例又使用 `policy.pth`。这些文件的存在不能证明其已经符合正式提交格式。**不能通过修改扩展名把 `.zip` 转成合格的 `.pth`。**应尽早拿到正式加载脚本，确认需要提交的权重、网络定义、推理代码和文件组织方式。

PDF 第 1 页提到代码、简短结果说明和约 10 分钟 slides，但附有 `for general projects` 的括注。因此，本项目是否也需要这些材料及相同展示时长，应另行确认。

## 4. 当前 Notebook 的示例配置

以下是查阅到的示例设置，不应直接当作已经确认的正式比赛接口：

- 游戏环境通过 `stable-retro` 与 `Gymnasium` 运行。
- 动作空间为 **17 个离散动作**，涵盖不动、移动、跳跃、拳脚及波动拳、升龙拳。
- 画面预处理裁去顶部约 12%，转换为灰度并缩放至宽 128、高 100。
- 环境包装使一次决策对应约 6 个游戏帧，并堆叠 4 帧；示例环境输出形状为 `(100, 128, 4)`。
- 基础训练使用 `Stable-Baselines3` 的 `PPO` 与 `CnnPolicy`。
- 非终局奖励以 `3 × 对敌造成的伤害 - 自身受到的伤害` 为基础，另有终局血量相关奖励，再乘以 `0.001`。
- 奖励代码注明留给学生修改；训练说明也提示应设计自己的训练过程。

训练、评估和最终推理应使用一致的画面处理、帧堆叠、通道顺序和动作映射。框架可能自行转换通道顺序，应避免重复处理。

环境中的六帧动作执行与“一帧内完成决策”的计算时限是不同概念。正式运行是否沿用上述包装、决策频率和预处理，需要通过老师的评测入口确认。

## 5. 建议实施流程与验收成果

| 阶段 | 主要工作 | 阶段验收 |
| --- | --- | --- |
| 1. 跑通环境 | 复制 Notebook，运行安装与环境配置单元；完成随机对战和动作演示 | 能启动环境、完成一局并保存回放 |
| 2. 统一接口 | 记录观察格式、动作映射、奖励与结束条件；统一环境版本 | 四人使用同一套训练和评估接口 |
| 3. 完成基础模型 | 训练 PPO 基线，保存配置、日志和 checkpoint；接通重新加载 | 基础模型能保存、加载并完成对战 |
| 4. 做改进实验 | 优先比较奖励设计，再选择少量训练参数或网络改动 | 在可比较条件下取得实验结果与解释 |
| 5. 评估和选择 | 比较胜率、获胜用时、血量、稳定性和推理延迟 | 选出最终模型及稳定备用模型 |
| 6. 验证提交 | 使用正式加载器，在新进程重新加载并运行完整对战 | 提交文件、动作输出与推理时限均满足要求 |

建议先得到一个完整可运行版本，再做有限改进。正式提交入口应与基础模型阶段同步接通，避免等训练结束才发现接口不兼容。

## 6. 四人分工建议

A、B、C、D 为占位符，由组员按能力和兴趣认领。每个人均负责自己模块的代码、实验记录、技术说明及对应讲解。

| 成员 | 主要责任 | 具体交付物 |
| --- | --- | --- |
| A：环境与集成 | 跑通老师环境；整理观察、动作、奖励和终止条件；统一包装与最终接口；中后期整合和排错 | 可运行环境、接口说明、动作回放、整合验证记录 |
| B：基础模型与训练 | 建立 PPO 基线；管理训练配置、日志、checkpoint 和恢复训练 | 基础模型、训练代码、配置、训练曲线 |
| C：改进与实验 | 研究奖励设计；比较少量训练参数或网络改动；分析收益和失败原因 | 改进模型、对比实验表、实验分析 |
| D：评估与提交 | 从第一天建立固定评测；统计对战指标和推理速度；对接加载器；汇总材料 | 评测代码、结果表、提交包、说明与展示材料汇总 |

D 负责汇总材料，不包办全组写作。A 完成环境后继续参与集成、失败回放分析和实验，保持工作量均衡。算法相关改动由 B、C 相互审阅，接口和提交相关改动由 A、D 相互审阅。

## 7. 实验、评估与协作约定

### 7.1 实验记录

每次训练建议记录：

- 实验编号、负责人及代码 commit。
- 环境版本、存档和输入处理方式。
- 算法、奖励设计、参数及随机种子。
- 训练步数、训练耗时和 checkpoint 位置。
- 评测条件、结果及下一步判断。

实验之间尽量只改变一个因素；对比算法或配置时说明训练预算差异。基础模型应保留，便于判断改动是否有效。

### 7.2 评估指标

| 指标 | 作用 |
| --- | --- |
| 胜、负、平及胜率 | 判断对战效果 |
| 获胜用时 | 对齐资格赛获胜后的排序依据 |
| 双方最终血量及血量差 | 分析失败和超时表现；保留数据以适配正式计分方式 |
| 回放及动作分布 | 排查无效动作、重复出招和异常结束等问题 |
| 完整 `act(state)` 的推理延迟与超时次数 | 验证实时决策要求 |

奖励提高不等于对战表现提高，应同时看上述结果。建议初筛每个候选模型运行约 20 局，最终候选增加评测局数；这些数量是实施建议，不是老师要求。

评测时冻结模型，固定并记录动作选择方式。示例视频使用的随机采样或少量对局，只能用于演示；最终应尽量匹配正式评测条件。推理测速应包括预处理、模型计算、设备传输和动作转换；具体毫秒预算以老师规定为准。

### 7.3 仓库使用

- 使用分支开展各模块工作，通过组内 review 合并。
- 共享环境配置、训练代码、评测代码和实验说明。
- 模型权重、训练日志和视频按约定单独保存，并在实验记录中注明获取位置；避免直接向普通 Git 提交大型产物。
- 定期保存和下载重要 checkpoint，避免云端会话结束后丢失工作。
- 修改前说明影响范围，尤其是动作编号、预处理和提交入口。
